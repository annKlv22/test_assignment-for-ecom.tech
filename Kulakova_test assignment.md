## Задание 2. «Создание заказа» – проверка API и обработки ошибок

**Неоднозначности + вопросы к аналитику/разработчику**:

1) Валидация user_id: должен ли пользователь существовать в системе? 
2) Дубли product_id в одном заказе формируют ошибку 400 или суммируются?

3) Границы quantity: есть ли максимум (например, 9999)? 
4) Если в заказе один товар не существует, а другого недостаточно, какой статус возвращаем (404 или 409)? 
5) Что происходит при добавлении пустого списка items? Возвращается ли ошибка?

**Чек-лист тестирования**

1) Корректный запрос → 201, id заказа, статус created	
2) Отсутствует user_id → 400	
3) У товара нет product_id или quantity → 400	
4) quantity = 0, -1, 1.5, "abc" → 400	
5) Пустой список items: → 400	
6) Несуществующий product_id → 404	
7) Остаток меньше quantity → 409	
8) Остаток равен quantity → заказ создан	
9) Сервис проверки остатков временно недоступен → 503	

**Тест-кейсы API**

1) ✅ Успешное создание заказа

Вводные: пользователь с user_id=15 существует. Товар 101 есть на складе ≥2 шт., а сервис остатков доступен.

Метод/endpoint: POST /orders
Тело: {"user_id": 15, "items": [{"product_id": 101, "quantity": 2}]}.

Ожидаемый результат: HTTP 201 Created, тело содержит order_id (число/строка), status: "created", товар 101 зарезервирован/списан на 2 шт.

2) ❌ Ошибка сервиса проверки остатков

Вводные: пользователь с user_id=15 существует, сервис остатков не работает.
Метод/endpoint: POST /orders
Тело: {"user_id": 15, "items": [{"product_id": 101, "quantity": 1}]}

Ожидаемый результат: HTTP 503 Service Unavailable. Заказ не создан, но после восстановления сервиса повторный корректный запрос → 201.

2) ❓ Некорректные данные

Метод/endpoint: POST /orders
Тело: {"user_id": 15, "items": [{"product_id": 101, "quantity": 0}]} (или quantity: -3, или отсутствует product_id).

Ожидаемый результат: HTTP 400 Bad Request, тело содержит описание ошибки валидации, заказ в БД не создан, остатки не изменились.

**Почему недостаточно проверять только HTTP-статус**

Можно сказать, что статус – лишь «обёртка» протокола. Чтобы убедиться, что заказ создан корректно, нужно дополнительно проверить тело ответа, логи, состояние базы данных (списались ли товары, есть ли они на складе), а также корректность и повторяемость запросов.

## Задание 3. SQL — базовые запросы

1) Пользователи из Москвы

SELECT id, name
FROM users
WHERE city = 'Москва';

2) Общая сумма оплаченных заказов по каждому пользователю

SELECT u.id, u.name,
       COALESCE(SUM(o.total), 0) AS paid_total
FROM users u
LEFT JOIN orders o
       ON o.user_id = u.id
      AND o.status = 'completed'   
GROUP BY u.id, u.name;

3) Пользователи, у которых есть хотя бы один returned-заказ

SELECT DISTINCT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 'returned';

4) Топ-3 пользователей по сумме оплаченных заказов
SELECT u.id, u.name,
       SUM(o.total) AS paid_total
FROM users u
JOIN orders o ON o.user_id = u.id
            AND o.status = 'completed'
GROUP BY u.id, u.name
ORDER BY paid_total DESC
LIMIT 3;

5) Пользователи, не сделавшие ни одного заказа

SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

6) Средняя сумма одного оплаченного заказа для каждого города

SELECT u.city,
       AVG(o.total) AS avg_order_total
FROM users u
JOIN orders o ON o.user_id = u.id
            AND o.status = 'completed'
GROUP BY u.city;
